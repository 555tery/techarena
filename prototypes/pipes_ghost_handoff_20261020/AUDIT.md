## Как устроен handoff

- `build.py` оставляет исходную таблицу в `parentEncoded`, а исправленные публичные адреса помещает в `encoded`. Команды не меняются.
- Во время replay `state` выполняет исправленный план. `oldPositions` и `oldTrench` одновременно записывают исходные координаты и длину траншеи по уже увиденным командам; второй полный allocator до расхождения не ведётся.
- При конце replay создаётся `reference` только если есть живая труба с другим адресом либо фактическая длина траншеи отличается от исходной. `importReference` восстанавливает геометрию по старым адресам уже созданных PID и `oldTrench`.
- Пока reference активен, на добавлении он считает свой plain Best-Fit `gx` и фактический plain Best-Fit `bx`. Фактический allocator берёт `gx`, только если `state.fits(gx, c)` и требуемая выкопка не больше выкопки для `bx`; иначе берёт `bx`. Reference всегда продолжает по собственному Best-Fit. Удаления применяются в обоих состояниях по одному PID.
- Ветка reference завершает обработку текущей команды через `continue`. Поэтому advanced `online` allocator не остаётся одновременно активным с устаревшим `state`; `Planner` получает наблюдение, но не выбирает адрес, пока reference существует. После синхронизации reference удаляется, а обычная ветка продолжает работу со следующей команды.

## Корректность и границы

В текущем `repair15` статическая попарная проверка декодированных исходных таблиц показывает **0 конфликтов адресов на общих командных префиксах**. Это важно: runtime бросает `parent prefix conflict`, если несколько ещё совпадающих публичных трасс дают разные исходные адреса. Для других профилей сборки эту проверку нужно повторять.

Ветка не использует команды после текущего входа: родительский адрес читается только для текущего `step`, пока вход совпадает с публичными таблицами. После mismatch ghost использует только импортированную прошлую геометрию и текущие команды. При условии корректных входных PID и неизменённого командного префикса схема online-корректна. Проверка `differing == 0 && state.T == reference.T` достаточна для равенства геометрии: длины труб и PID одинаковы, а активные начала труб и граница траншеи совпадают.

Условие по `digs` даёт лишь локальный предел на текущую команду. Оно не доказывает отсутствие будущей потери KPI: другое размещение способно фрагментировать свободные интервалы и увеличить выкопку позднее. Поэтому название `canonical_choices` в счётчике означает выбор адреса ghost, а не доказанное восстановление исходного KPI.

При активном reference код сознательно отключает и online-эпизод, и поиск `Planner`; фактическое продолжение в этот период — BF с ограниченной подсказкой ghost. Это сохраняет простое синхронное состояние, но может отличаться от старого продвинутого fallback даже при такой же геометрии в начале mismatch. Если reference не синхронизируется, этот режим может длиться до конца потока.

Reference создаётся только на физически изменённом префиксе и копирует вектор PID/строит карты свободных интервалов один раз. По переданному координатором результату, предыдущий cache32 parent доходил до 128 MiB; память текущего ghost-варианта не измерялась. Лимит 256 MiB всё равно нужно проверить на длинном фрагментированном потоке. Аналогично, импорт сортирует активные интервалы; его CPU-стоимость не измерялась здесь.

## Проверки для следующего gate

Эти проверки перечислены, но здесь не запускались:

1. Open15: точное совпадение команд/адресов кандидата и score с заявленным Open15 максимумом; на неизменённой геометрии reference не должен создаваться.
2. Направленные ветви после короткого и длинного префикса: Open11-p2, Open11-p8, Open8-p402 и Open8-p410. Сравнить исходный parent, repaired replay без ghost и `repair15` с ghost.
3. Handoff на положительной команде и на удалении; PID не должен дублироваться или теряться, ответ на каждую входную команду должен выводиться ровно один раз.
4. Отдельно ветви `blocked` и `extra_dig_rejected`; проверить границу траншеи около кратных 20, включая ghost-адрес в хвостовом интервале.
5. Синхронизация после удаления последней отличающейся трубы и случай, когда адреса совпали, но `T` ещё различается. После сброса reference следующая команда должна пройти обычной веткой ровно один раз.
6. 200k команд с большим числом интервалов: CPU/RSS, включая случай, где reference живёт до конца потока. После этого нужен независимый набор новых продолжений; условие локальной выкопки не заменяет paired KPI gate.
