# SEARCH-v3: подготовка без экспериментов

Статус: **prepared_not_run**. Генерация входов и проверки Python не запускают
кандидата, compiler, interactor, модель или эволюцию. Текущий SEARCH-v2 не переключался.
Baseline для v3 ещё не выбран и не измерен; бюджет следующего запуска не назначен.

## Основной набор и отдельный стресс

- `task/data/search`: **128 новых потоков, 16 семейств × 8 вариантов**.
  10 434 403 операции; 6 036–200 000 операций на поток.
- Во всех основных потоках **F/B ≥ 0,95**, среднее 0,966865;
  минимум F/P — 0,950054. P — исторический пик живого объёма,
  B = 20·ceil(P/20), F — финальный живой объём.
- Не меньше 9,98% операций — удаления. Сохраняются разнообразные размеры,
  live set, lifetimes, FIFO/LIFO, фазы, серии, дрейф и cohort-потоки.
- `stress/data`: **32 новых потока, 16 семейств × 2 варианта**,
  2 222 710 операций; F/B = 0,03827–0,25. После самостоятельного churn идёт
  явно заданная разгрузка; дополнительного заполнения нет.
- Stress исключён из fitness, отбора, архива и feedback модели.
  Его запуск не автоматический; entrypoint не принимает `--split`.
  Это диагностический материал, **не новый holdout**.

## Как получены входы

`generate.py` использует новые SHA256-derived seeds с разными namespaces
для main/stress и неизменные функции генератора v2. Изменения относятся только к v3:
диапазон вероятности удаления 0,10–0,49, ограничение target для коротких горизонтов
и отсутствие завышенной начальной загрузки в `distribution_switch`.
Параметры большого live set сохранены из v2.

Основной поток заканчивается в **последней подходящей естественной точке
последней четверти горизонта**, после churn, при F/B ≥ 0,95.
Заполняющий хвост не добавляется. При отсутствии такой точки используются
следующие seed и начало фаз по заранее заданному правилу: максимум 32 попытки,
фактически потребовалось максимум 6. Фильтрация использует только свойства входа.
Это намеренное условное распределение, а не случайная выборка реальной нагрузки.

Все 160 входов проверены структурно и независимым существующим parser.
Seed и SHA256 различаются внутри v3, между main/stress и с SEARCH-v1/v2.
Validation и Open15 не открывались, поэтому пересечение с ними не проверялось.
Ранее известные результаты SEARCH повлияли на постановку v3, но результаты
кандидатов не использовались для отбора конкретных входов.

## Fitness и evaluator

`fitness = (1/16) · Σ_family [(1/8) · Σ_case F/T]`.

Это прямой KPI задачи с выбранными равными весами семейств. Официальные скрытые
веса неизвестны. Максимум отдельного потока ограничен F/B, а не обязательно 1.
B/T, средний перерасход T/B−1, худшие 16 main-потоков и семейства остаются
диагностикой; они не добавляются к fitness. CPU записывается отдельно;
автоматический tie-break в отборе Shinka здесь не реализован.

Подготовлен отдельный `evaluator.py` поверх проверенного native engine:
2 потока по умолчанию, официальный checker, те же CPU < 5 s и RSS < 256 MiB.
Требуются все 128 корректных результатов, точные hash/объёмы/число команд/веса,
конечные CPU/RSS/KPI и согласованность официального F/T.
Любая ошибка протокола, неполное покрытие или превышение лимита отклоняет кандидата.

`load_search()` проверяет только main-входы и support; stress даже не читается
маршрутом fitness. Выходы будущих оценок разрешены только в новых каталогах
`search-v3/evaluations/`; результаты можно затем опубликовать в будущий каталог Shinka.
Native support и v2 snapshot используются только для чтения и закреплены хешами.
Новые сборки, измерения parity и baseline сейчас **не выполнялись**.

## Подготовка следующего запуска

`task/shinka.yaml` и `next-run.json`: Astra xhigh Fast, subscription billing,
2 evaluator workers, до 3 попыток применения патча с feedback в одном поколении.
Отдельный `headless.sh` проверяет baseline именно v3 и не зависит от baseline/каталогов
v2; без нового run manifest и полного baseline модель не вызывается.
План требует существующий feedback-repair manager, а не vanilla Shinka runner.
Автозапуск/менеджер нового прогона не создавался; при отдельном запросе на запуск
нужно выбрать seed и бюджет, собрать из этого плана новый запуск и пройти baseline gate.
Материалы H1–H6 остаются в `../search-v2/research/`; они не требуют изменения текущего прогона.

Безопасные команды из корня проекта:

```sh
shinka-pipes/.venv/bin/python -B shinka-pipes/search-v3/entrypoint.py --check
shinka-pipes/.venv/bin/python -B shinka-pipes/search-v3/check.py
shinka-pipes/.venv/bin/python -B -m unittest discover -s shinka-pipes/search-v3 -p 'test_*.py' -v
```

Доказательства: `preparation.json`, `verification.json`, `snapshot.json`,
`source-guard.json`, два manifest. `preparation-drafts/` содержит сохранённую
незавершённую генерацию входов с прежним warmup; к проверяемому корпусу она не относится.
