## Разнообразие

| Семейство | Что меняется |
|---|---|
| uniform_churn | Равномерные размеры, интенсивность удаления, live set |
| short_heavy / long_heavy | Преобладание коротких или длинных труб |
| bimodal | Смесь коротких и длинных труб |
| section_boundaries | Размеры около 20 и 40, включая соседние значения |
| fifo / lifo | Порядок удаления по возрасту |
| size_lifetimes | Связь размера и времени жизни, меняющая знак по фазам |
| burst_drain | Пакетные вставки и неполные массовые удаления |
| distribution_switch | Смена распределения размеров и давления на live set |
| drifting_sizes | Постепенное изменение типичного размера |
| striped_recycling | Чередование размеров и разреженные удаления когорты |
| geometric_cohorts / additive_cohorts | Серии одинакового размера с разным ростом |
| large_live_set | Большое число одновременно живых труб и 200k команд |
| size_biased_deletion | Предпочтительное удаление маленьких/больших труб |

Validation дополнительно содержит по два сценария четырёх отсутствующих в search
механизмов: постоянные pins с churn, тяжёлые хвосты времени жизни, переключение
политики удаления и отложенное вложенное освобождение когорт. Это ограниченный
сдвиг распределения; он не покрывает все возможные потоки и не доказывает обобщение.

## Fitness

Для потока `P` — максимальный суммарный объём живых труб, `B=20*ceil(P/20)`,
`T` — длина траншеи кандидата. Метрика потока — `B/T`, затем среднее внутри
семейства и среднее по семействам с равным весом. Диапазон — `[0,1]`.

Для положительного финального объёма `F` это равно `(F/T)/(F/B)`: KPI,
нормированному на объёмную верхнюю границу KPI. Так низкая финальная заполненность
после массовых удалений не уменьшает вес сценария. `B` — нижняя граница, а не
гарантированно достижимый optimum: фрагментация может требовать большей траншеи.

Все случаи должны пройти interactor, иметь измеренные CPU < 5 s и RSS < 256 MiB.
Пропуск, дубликат, неправильный hash, ошибка протокола или лимита отклоняют кандидата.
В feedback идут только search-метрики. Worst-family и raw KPI — диагностические
поля; они не меняют формулу fitness. Проверенный search-score baseline — 0.914983819101.

## Validation и Open15

Validation не запускается автоматически ни для поколений, ни для найденного best.
После выбора кандидата отдельная команда фиксирует копию исходника и SHA256,
проверяет baseline и кандидата на одном наборе и сохраняет сравнение вне `runs/`.
Результат автоматически не возвращается Shinka. Повторный подбор по validation
сделает его частью процесса обучения; при таком использовании потребуется новый набор.

Безопасная проверка входов (без solver):

```sh
/Users/555tery/techarena/shinka-pipes/.venv/bin/python /Users/555tery/techarena/shinka-pipes/validate.py
```

Будущая реальная validation требует отдельного разрешения и явного `--run`:

```sh
.venv/bin/python validate.py --run --program_path /absolute/path/candidate.cpp --results_dir validation-results/new-check
```

Open15 исключён из active task и всех этих evaluator-маршрутов. Проверяются только
его контрольные суммы. Он уже влиял на создание baseline, поэтому независимым
финальным holdout не является. Сохранены оригиналы и старая копия; хеши находятся
в `corpus-protocol.json`. Платформа не используется.

## Проверка подготовки и границы изоляции

Манифесты фиксируют seed, параметры, статистику, SHA256 каждого входа и генератора.
`corpus-preparation.json` фиксирует объём наборов; `task-synthetic/snapshot.json`
закрепляет задачу и supporting code. Повторная генерация отказывается перезаписывать
существующие наборы. Исходники генератора находятся в `generate_synthetic.py`.

Структура входов проверяется отдельным audit и существующим parser harness без
запуска interactor. Tests проверяют разделение и fitness на искусственных отчётах.
Сквозная компиляция/оценка baseline проверена на search. Модель и эволюционный
цикл не проверялись запуском; validation и Open15 в этом прогоне не использовались.

Разделение обеспечивается маршрутами evaluator, расположением наборов и инструкциями
агенту. Локальная папка не является системной песочницей: raw validation/Open15 не
следует вручную давать модели, а для недоверенного кода нужна отдельная OS-изоляция.
