# Ускоренный evaluator SEARCH-v2

18 октября 2026 подготовлена отдельная версия. К текущей Shinka она **не подключена**.
Полная [сверка baseline](comparisons/20261018-baseline-search-v2/REPORT.md) на 128 SEARCH-v2
подтвердила совпадение результатов и сокращение времени на 21.6%.
Эволюция и модели не запускались; validation и Open15 не читались.

## Что изменено

Вместо двух stdout-reader threads и передачи каждой строки через Python Queue
используется один цикл `selectors.DefaultSelector`: на macOS это kqueue.
Он читает доступные байты обоих stdout, сохраняет порядок каждого канала и
воспроизводит разбиение исходного `readline(4097)`. Неполная строка ждёт LF,
достижения лимита или EOF. Stderr по-прежнему независимо дренируют исходные threads.

[`fast_harness.py`](fast_harness.py) загружает отдельный объект исходного harness,
меняет только транспортные привязки на время одного `run_case`, затем закрывает
selector. Исходники активного запуска и глобальные модули Python не правятся.
Обычная буферизация оставлена как промежуточный вариант для сравнения.

## Что сохранено

- Официальные `interactor.cpp` и `testlib.h`, проверки диапазонов, пересечений,
  роста траншеи, позиций при удалении и расчёт T/KPI — прежние байты исходников.
- Прежние функции `run_case`, `wait_line`, `read_response`, `reap_with_stats`,
  `terminate_and_reap` и `main` исполняются из закреплённого исходного модуля.
- Один интерактивный запрос и ответ в прежнем порядке; запись и flush не меняются.
  Ограничения формата, 4096 bytes, числа токенов, LF, EOF и stdout после `0` прежние.
- Response timeout 5 s, wall 180 s, выход после `0` за 2 s. Свежие CPU и RSS
  именно solver через прежний `wait4`: CPU < 5 s, RSS < 256 MiB.
- Для положительного результата нужны все 128 SEARCH-v2, по 8 на 16 семейств,
  те же хеши файлов и проверки защищённой части кандидата. Сокращения набора нет.
- Используется прежняя `aggregate_report`: среднее B/T внутри каждого семейства,
  затем среднее по семействам, с прежним порядком суммирования и проверками записей.

[`reference.py`](reference.py) проверяет SHA256 эталонного snapshot и всех 33 файлов
поддержки. Изменение эталона блокирует запуск; автоматического repin нет.
`--check` хеширует только поддержку и SEARCH manifest, не входные потоки.

## Проверка

В [verification.json](evidence/verification.json) сохранены **20 успешных тестов**,
хеши реализации и неизменность 33 файлов эталона до и после проверки.
В их числе 25 интерактивных сценариев, каждый на трёх вариантах транспорта:
исходном, BufferedReader и selector — всего 75 коротких fixture-прогонов.

Проверены корректные и фрагментированные ответы, signed integers, строка ровно
на границе лимита, stderr 256 KiB, EOF, отсутствие LF/flush, частичный ответ,
лишние/недостающие/нечисловые токены, длинные строки, пересечение, выход за траншею,
ошибочная позиция удаления, stdout после `0`, отсутствие завершения и ненулевой exit.
Проверены EOF/error/EINTR/EAGAIN транспорта, очистка процессов и threads,
прежние отказы агрегации на CPU/RSS/NaN/Inf, дубли и неполное покрытие.
Ресурсные границы проверялись на записях в памяти, без нагрузочных запусков на 5 s/256 MiB.

Проверка скопированного Shinka entrypoint выполнялась только с `--check`;
маршрут компиляции/evaluation проверен с подставленными результатами subprocess.
Настоящий кандидат и SEARCH-входы в этих тестах не исполнялись.

## Предварительный замер транспорта

Искусственный поток: [selector-benchmark.json](evidence/selector-benchmark.json).
Искусственный поток из 32768 вставок, длины 1–40, простой append-only клиент,
неизменённый официальный checker. Пять повторов каждого варианта с перестановкой
порядка; ниже медианы wall только `run_case`, без компиляции.

| Транспорт | Медиана, s | Относительно исходного |
|---|---:|---:|
| Исходный | 1.445225 | 1.00× |
| BufferedReader + threads/Queue | 1.276633 | 1.13× |
| Selector | 1.012342 | **1.43×** |

Время сократилось примерно на **30%**. Во всех 15 прогонах совпали T, B/T, KPI
и SHA256 полного transcript. CPU/RSS измерялись заново и прошли прежние пороги.
Первый замер сохранён как `transport-benchmark.json`.

## Полный SEARCH v2

В [контролируемом сравнении](comparisons/20261018-baseline-search-v2/REPORT.md)
полное время evaluator составило **409.883 → 321.451 s**: **1.275×**, или **−21.57%**.
Все 128 результатов, 16 оценок семейств, combined score `0.9572740109816693`
и SHA256 всех протоколов совпали; CPU/RSS прошли прежние лимиты.
Ускоренная версия быстрее по wall на 119/128 потоках и на всех 16 семействах в сумме.
Сумма CPU solver немного выросла; выигрыш относится к wall evaluator.

Основная Shinka была остановлена пользователем во время первого замера;
поэтому исходная версия один раз повторена. Итоговый коэффициент использует
два полных запуска при остановленной Shinka. Первый замер сохранён отдельно.
Это одна пара измерений на данном baseline. Ускоренная версия к основному прогону не подключена.

## Использование после разрешённого переключения

[`evaluate.py`](evaluate.py) принимает прежние `--program_path` и `--results_dir`.
При копировании Shinka нужно указать `PIPES_FAST_EVALUATOR_ROOT` на этот каталог.
Результаты должны идти в новый каталог вне существующих Shinka runs; перезапись
готовых metrics/harness запрещена. Текущие конфигурации не менялись.

Без исполнения кандидатов:

```sh
shinka-pipes/.venv/bin/python -B shinka-pipes/evaluator-fast/evaluate.py --check
```

Транспорт рассчитан на прежний последовательный запуск случаев. Тайминги и
ресурсные значения между запусками могут отличаться. При большом запрещённом
выводе после `0` причина отказа может стать timeout вместо protocol_error:
до ожидания выхода stdout не дренируется отдельным thread; принятия такого вывода нет.

[Предыдущий анализ](../analysis/20261018-evaluator-speed/REPORT.md) содержит
замеры сохранённого baseline и оставшиеся варианты ускорения.
