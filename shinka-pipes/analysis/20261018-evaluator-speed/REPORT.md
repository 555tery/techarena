# Ускорение evaluator SEARCH v2

18 октября 2026. Основной резерв — транспорт интерактивных команд: буферизация чтения,
устранение передачи каждой строки через Python threads/Queue и буферизация файла протокола.
Кэш компиляции полезен как вспомогательная мера: вся работа вне таймеров отдельных
потоков заняла около 7 секунд из 442. Ускоренная реализация пока не создана и не измерена.
Текущий прогон и его исполняемые исходники сохранены; новые проверки кандидатов не запускались.
Validation и Open15 не открывались.

## Замеры существующего baseline

Источник — уже завершившееся поколение 0 запуска SEARCH-v2
`20261018T011836+0700-084000`, точная копия поколения 2 прошлого SEARCH-v1.
[Исходный summary](../../search-v2/runs/20261018T011836+0700-084000/gen_0/results/harness/summary.json)
содержит 128 успешных записей. Происхождение, хеши и агрегаты сохранены в [evidence.json](evidence.json).

| Величина | Значение |
|---|---:|
| Полная оценка по журналу Shinka | 442.25 s, около 7 мин 22 с |
| Сумма wall-таймеров 128 интерактивных потоков | 435.27 s, около 7 мин 15 с |
| Вне таймеров потоков, приблизительно | 6.98 s, 1.6% |
| CPU решения, user + system, сумма | 64.22 s |
| CPU interactor, user + system, сумма | 82.93 s |
| Команды / строки команд и ответов | 10 870 000 / 21 740 128 |
| Сбросы файла протокола через endl | 10 870 000 |
| Объём файлов протокола | 63 163 905 bytes |

Wall и CPU измеряют разные вещи: разность этих чисел не является профилем Python.
В 6.98 s входят сборка, импорт, аудит входов, подготовка и завершение; отдельного
замера компиляции нет. Для этого baseline устранение всей этой части сэкономило бы
лишь около 1.6%. Это основание сначала ускорять интерактивный цикл.

## Чтение stdout без посимвольных системных вызовов

В [pipes_harness.py](../../search-v2/task/tools/pipes_harness.py) оба Popen используют
`bufsize=0`, а `start_line_reader` вызывает `stream.readline(MAX_RESPONSE_LINE + 1)`.
Получается raw FileIO: базовая реализация readline в CPython 3.12 при отсутствии peek
читает по одному байту. На миллионах строк это создаёт большой объём мелких read.
Это вывод из [кода CPython 3.12.11](https://raw.githubusercontent.com/python/cpython/v3.12.11/Modules/_io/iobase.c)
и [семантики bufsize](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen),
а не результат профилирования запущенного процесса.

Первое изменение для отдельной будущей версии — BufferedReader только на читающей
стороне stdout, с тем же ограниченным readline. Запись команд, явные flush и все
проверки формата остаются прежними. Официальный interactor при этом не меняется.
Нельзя заменить readline на блокирующий read большого фиксированного объёма:
ожидание заполнения буфера может остановить интерактивный диалог. Альтернатива —
read1 или неблокирующее чтение доступных байтов с явным разбором строк.
[Документация io](https://docs.python.org/3.12/library/io.html#io.BufferedReader).

## Файл протокола без сброса после каждого ответа

[interactor.cpp](../../search-v2/task/vendor/interactor.cpp), строки 36 и 62,
пишет каждый ответ в `tout` через endl. Это отдельный файл judge_output.txt;
команды участнику отправляются другим потоком, cout. По [стандарту C++](https://eel.is/c++draft/ostream.manip#lib:endl)
endl добавляет перевод строки и вызывает flush. Получается 10.87 млн сбросов
при общем размере transcript около 63 MB.

В отдельной версии можно заменить endl на перевод строки только в `tout`, оставив
буферизацию файла и обязательный сброс при завершении/обработанной ошибке.
В testlib `registerInteraction` открывает tout как файл, а `InStream::quit` закрывает
его перед halt. Обычный выход также должен сохранить полный transcript.
При принудительном убийстве процесса хвост буфера может потеряться; диагностику
этого случая нужно явно сохранить. Transcript не используется для принятия решения
о корректности, но остаётся важным артефактом разбора ошибок.

Flush команд через cout, ответов решения и каналов relay сохраняется.
Все проверки диапазонов, пересечений, удаления PID и расчёт траншеи остаются прежними.
Это изменение создаёт новую сборку interactor с новым хешем; подключать её к текущему
замороженному прогону нельзя. Если нужен буквально прежний исходник interactor,
этот шаг пропускается, остальные меры остаются применимы.

## Передача строк без Python Queue

На каждый вход есть строка команды и строка ответа, на поток — ещё финальный 0.
Сейчас каждая строка проходит reader thread и Queue: около 21.74 млн put и столько же
get. Далее Python проверяет числа и заново формирует строку ответа для interactor.

Если после буферизации этот путь всё ещё дорог, следующий вариант — отдельный C++
runner для одного потока: он запускает прежние solver/interactor, передаёт строки,
проверяет протокол и собирает wait4/rusage конкретного PID решения. Python сохраняет
интерфейс evaluator, JSON-артефакты и прежний aggregate_report. CPU самого runner
не должен попадать в solver CPU; RSS берётся от решения, с прежним переводом единиц.

Менее крупная альтернатива — один Python event loop с неблокирующими pipes вместо
двух reader threads/Queue. [DefaultSelector](https://docs.python.org/3.12/library/selectors.html#selectors.DefaultSelector)
поддерживает pipes на Unix. Выбирать между этим вариантом и C++ следует после замера
буферизованной версии, а не писать обе реализации одновременно.

Таймаут Queue.get в 20 ms не означает задержку 20 ms на каждую команду:
при появлении элемента get возвращается сразу. Простое уменьшение этого таймаута
не устраняет стоимость строк и межпоточной передачи.

## Вспомогательные изменения

| Изменение | Условия сохранения проверок | Ограничение пользы |
|---|---|---|
| Кэш сборки interactor | Ключ включает исходник, testlib, flags, compiler/toolchain, target и SDK; проверяется хеш бинарника | Вся работа вне потоков сейчас около 7 s |
| Кэш разбора входов | Свежий SHA256 фактических байтов; кэш связан с SHA, версией parser и схемой метаданных | Нельзя доверять только имени, размеру или mtime |
| Ранний отказ ошибочного кандидата | Остановиться только после доказанной ошибки; correct=false, непроверенные потоки отмечены как skipped | Не ускоряет полностью корректный baseline |
| Запись stderr блоками в файл | Продолжать постоянно читать stderr, сохранять диагностику и EOF | Основной выигрыш для многословных/ошибочных программ |

Кэш разбора не должен добавлять возможность использовать вход, отличный от проверенного
по хешу; снимок корпуса и путь исполнения должны оставаться согласованными.
Положительная оценка по-прежнему требует всех 128 успешных потоков. Отказ по плохому
промежуточному score, сокращение набора или повторное использование старых CPU/RSS
не входят в эти предложения.

## Что сохраняется в ускоренной версии

- Тот же исходник кандидата, compiler flags, 128 файлов и их хеши; все 16 семейств по 8 потоков.
- Та же семантика официального checker: рост по 20, диапазоны, пересечения, PID,
  освобождение, final occupied volume и T. Удалять проверку клеток или заменять её
  непроверенным собственным судьёй не требуется.
- Следующая команда приходит только в прежнем порядке после ответа на текущую.
  Нельзя заранее подать весь поток в stdin или использовать пакетный режим решения.
- Сохраняются 2 целых на вставку, 1 на удаление, грамматика целых и нормализация ответа,
  максимум 4096 bytes, перевод строки, отказ на пустые/лишние/некорректные токены.
- Сохраняются таймаут ответа 5 s, общий wall 180 s, завершение после 0 за 2 s,
  проверка отсутствия stdout после 0, обработка EOF, кодов выхода и очистка дочерних процессов.
- Сохраняются свежие per-process wait4 CPU и ru_maxrss: CPU < 5 s и RSS < 256 MiB.
  Секунды разных запусков не обязаны совпадать; определение измерения и пороги сохраняются.
- Прежние проверки полноты/уникальности записей и конечности чисел остаются в aggregate_report.
  B = 20 ceil(peak_live_volume / 20), score — среднее B/T внутри семейства, затем по семействам.
  Порядок суммирования сохраняется, чтобы не менять результат округления float.

## Параллельные проверки

Несколько потоков параллельно могут сократить wall, но меняют конкуренцию за CPU/память
и могут повлиять на ресурсные отказы около порога. Нельзя объединять rusage разных PID,
использовать wall вместо CPU или переносить старые измерения. Результаты необходимо
собирать в прежнем порядке перед агрегацией. Поэтому параллелизм не является первым
шагом для требования сохранить строгую сопоставимость проверок.

## Порядок подготовки и последующей проверки

1. Создать отдельную версию evaluator, сохранив текущий snapshot и routing SEARCH-only.
2. Добавить ограниченный BufferedReader; официальный checker оставить прежним.
3. Отдельно подготовить буферизацию transcript, если допустима новая сборка interactor.
4. Рассматривать новый relay только после измерения остаточной стоимости обмена.
5. После отдельного разрешения сопоставить старую и новую версии на одном сохранённом
   baseline и том же SEARCH-v2. Требуются одинаковые T/B по каждому потоку,
   family_scores и combined_score, свежие CPU/RSS с прежними порогами.
6. Отдельно проверить ошибочные протоколы: нет flush, ответ без LF/длиннее лимита,
   пустые/лишние/нецелые токены, досрочный EOF, вывод после 0, ненулевой выход,
   пересечение, неверный PID/shift, выход за траншею, превышение CPU и RSS.
   Разбиение строк на любые порции и нагрузка на stderr не должны скрывать ошибку.

На этом этапе выполнены только чтение кода и агрегация уже существующего baseline.
Сборки, тесты изменённого транспорта и новые измерения кандидатов не запускались.
