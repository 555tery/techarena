# Native evaluator SEARCH-v2

18 октября 2026 evaluator **подключён к возобновлённой SEARCH-v2 Shinka** по
прямому запросу пользователя: 2 потока, прежние модель и бюджет 30 поколений.
Поколения 0–4 сохранены; прерванный кандидат 4 прошёл 128/128 и записан в базу.
Продолжение с поколения 5 работает в отдельном каталоге с той же базой; старые
артефакты не перемещались. Validation и Open15 не подключены.
[Данные подключения](resumes/20261018T025030+0700-continuation/plan.json).

## Что ускорено

- Интерактивный обмен перенесён из Python в C++: официальный checker сам
  управляет отдельным solver через pipes. Убраны Python relay, Queue,
  переключения Python threads и отдельный процесс checker.
- В копии checker заменены ровно два `endl` **журнала** `tout` на `\n`.
  Команды solver по-прежнему немедленно отправляются через `cout` с flush.
  Полный transcript сохраняется; успешный выход обязательно сбрасывает буфер.
- Независимые потоки SEARCH можно исполнять параллельно (`--workers 1..8`).
  Результаты собираются в прежнем порядке, независимо от порядка завершения.
  По выбору пользователя default — **2**: 70.7 s на полном baseline и существенно
  меньшие затраты CPU. Режим **8** доступен вручную: в замере он занял 63.3 s.
  Численные результаты — в отчёте ниже.
- Бинарник checker кэшируется по исходникам, флагам, компилятору, SDK,
  платформе и хешу окружения; целостность проверяется при каждом обращении.
  Solver каждый раз компилируется заново. Результаты и замеры ресурсов не кэшируются.
- После доказанной ошибки корректности или превышения ресурсов новые потоки
  не выдаются. Уже начатые завершаются; остальные помечаются `skipped`.
  Такой кандидат получает `correct=false` и score 0, частичный score не принимается.

## Сохранённые проверки

Исполняется функция исходного официального checker с прежним `testlib.h`:
границы, пересечения, рост траншеи, PID и координаты удаления, T/KPI.
Изменения двух строк журнала проверяются при сборке; исходники snapshot не меняются.
[`build_native.py`](build_native.py) и [`native_runner.cpp`](native_runner.cpp)
содержат преобразование и транспорт.

Сохраняются одна строка ответа, LF, лимит 4096 bytes, точное число целых токенов,
signed integers, проверка EOF и запрет stdout после `0`. Response timeout — 5 s,
wall — 180 s, выход после `0` — за 2 s. Зависание, ненулевой exit и отсутствие
измерения ресурсов отклоняют кандидат.

Для **каждого** solver заново измеряются CPU user+system и пиковый RSS через
POSIX `wait4` его PID: **CPU < 5 s, RSS < 256 MiB**, без деления на число workers.
Ресурсный отчёт идёт по отдельному pipe, закрытому у solver до `exec`;
solver не может подменить его обычной записью файла в рабочем каталоге.
Диагностические ресурсы checker измеряются отдельно через `getrusage(RUSAGE_SELF)`.

Прежняя `aggregate_report` требует 128/128 успешных SEARCH-v2 и свежие конечные
ресурсные значения. Coverage, SHA256 входов, защищённая часть C++ и 33 файла
эталона проверяются. Fitness прежний: среднее B/T внутри каждого семейства,
затем среднее 16 семейств, с исходным порядком сложений floating point.

## Проверка реализации

[`native-parallel-tests-final.json`](evidence/native-parallel-tests-final.json):
9 успешных тестовых методов на искусственных данных. Они проверяют точные
результаты и transcript против прежнего selector + официального checker,
форматные ошибки, EOF/LF/flush, таймауты, stderr под нагрузкой, ошибки геометрии,
огромные целые и ведущие нули, заранее выданные ответы, stdout после `0`,
свежие раздельные CPU, реальное превышение RSS, остановку после ошибки,
parallel/serial parity, порядок записей и очистку дочерних процессов.

Проверка RSS использует отдельный искусственный клиент с большим рабочим
набором; его фактический RSS проверяется, размер allocation не подставляется
вместо измерения. Предыдущая версия fixture оказалась нестабильна: фактический
RSS был ниже порога при большем allocation; неудачный тест сохранён отдельно.

Полные baseline-измерения и сравнение всех 128 transcript —
в [отчёте о параллельном запуске](comparisons/20261018-parallel/REPORT.md).
[Первый native serial замер](comparisons/20261018-baseline/summary.json)
получил 106.338 s и прежний score `0.9572740109816693`.
В нём поле диагностического CPU checker включало уже учтённый CPU solver;
это исправлено в последующей версии. Измерение CPU solver и проверка лимита
в первом замере были корректны.

## Использование

Проверка поддержки и подготовка бинарника без исполнения кандидатов:

```sh
shinka-pipes/.venv/bin/python -B shinka-pipes/evaluator-native/evaluate.py --check
shinka-pipes/.venv/bin/python -B shinka-pipes/evaluator-native/evaluate.py --prepare
```

[`evaluate.py`](evaluate.py) принимает прежние `--program_path`, `--results_dir`
и дополнительный `--workers`. Результат должен идти в новый каталог вне
существующих Shinka runs; перезапись готовых metrics/harness запрещена.
При копировании entrypoint Shinka нужно задать `PIPES_NATIVE_EVALUATOR_ROOT`
абсолютным путём этого каталога. Автоматического возобновления нет.

Текущая Shinka использует [`shinka_evaluate.py`](shinka_evaluate.py): native
артефакты пишутся в новый внешний каталог, а metrics/correct и ссылка на полный
harness публикуются в каталог поколения. У gen4 используется `native-results`;
старый частичный `results` сохранён. Восстановление идёт через штатные очередь
и запись Program, с прежними parent/inspirations и без повторной генерации патча.
Исходные 33 файла snapshot не меняются; перед продолжением сделана SQLite backup.
5 проверок подключения без моделей — [shinka-continuation-tests.json](evidence/shinka-continuation-tests.json).
Они также проверяют baseline gate: hash evaluator сохранённого baseline остаётся
прежним, hash активного native wrapper записывается отдельно. При первом
подключении смешение этих полей заблокировало вызов модели; старый неудавшийся
старт 5 сохранён, Program для него не создавался и бюджет не увеличивался.

`--workers 1` оставляет native транспорт и даёт последовательный запуск.
CPU/RSS и wall зависят от нагрузки на компьютер; параллельность не отменяет
лимиты. Приведённое ускорение относится к этому baseline и этому компьютеру.
Проверки полноты и корректности остаются обязательными для каждого нового кода.
