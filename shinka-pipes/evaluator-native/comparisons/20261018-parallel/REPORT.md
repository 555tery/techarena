# Полный baseline: native evaluator и параллельность

18 октября 2026. Только сохранённый baseline на всех **128 SEARCH-v2**.
Основная Shinka остановлена; эволюция, модели, validation и Open15 не использовались.

## Результат и выбранный default

По запросу пользователя default — **2 потока**: **70.672 s**.
Это **5.80×** относительно сохранённого исходного
замера и **4.55×** относительно selector.
Восемь потоков в этом замере были быстрее, но требовали примерно вдвое больше CPU.
Смена default не подключает evaluator к остановленной Shinka и не возобновляет её.

| Вариант | Полное время, s | Максимальный CPU solver на поток, s | Максимальный RSS solver, MiB |
|---|---:|---:|---:|
| Исходный последовательный, сохранённый замер | 409.883 | 1.327 | 8.875 |
| Selector последовательный, сохранённый замер | 321.451 | 1.708 | 8.250 |
| Native последовательный, первый замер | 106.338 | 1.190 | 12.188 |

Это полное время evaluator: хеши/проверка подготовки, свежая компиляция solver,
исполнение 128 потоков и агрегация. Native checker уже собран; его первоначальная
сборка учитывается отдельно в `preflight.json`. Результаты solver не кэшируются.

Варианты 2/4/8 исполнялись последовательно в указанном порядке, по одному полному
замеру каждого. Исходный, selector и первый native serial — сохранённые более ранние
замеры при остановленной основной Shinka. Это измерения этого baseline на этом
ноутбуке; фоновые нагрузки и температура не контролировались лабораторно.
Коэффициенты не являются гарантией для произвольного кандидата или компьютера.

## Затраты CPU и выбор параллельности

| Workers | Сумма CPU solver, s | Сумма CPU checker, s | Всего CPU, s |
|---|---:|---:|---:|
| 2 | 68.156 | 57.016 | 125.172 |
| 4 | 122.380 | 108.941 | 231.320 |
| 8 | 137.861 | 115.361 | 253.223 |

Четыре потока здесь не дали выигрыша по wall; восемь сократили wall примерно
на 10% относительно двух ценой роста CPU. Параллельность не масштабирует
ресурсные лимиты. CPU solver и checker учитываются раздельно, пик RSS — отдельно
по каждому PID. `wall_sum_s` складывает длительности пересекающихся случаев,
поэтому это не время ожидания полного параллельного evaluator.

В первом native serial отчёте диагностический CPU checker включал уже reaped
solver. Это исправлено через `getrusage(RUSAGE_SELF)` и проверено fixture-тестом;
измерение solver и его лимит в том первом отчёте были корректны. Для анализа
общих затрат CPU используются только новые 2/4/8, где двойного учёта нет.

## Что ускорено и что сохранено

Обмен checker/solver выполняется внутри native C++ driver; Python больше не
пересылает каждую команду и ответ. Два flush журнала `tout` заменены буферизацией,
при этом отправка команд и обязательный flush ответов сохраняются. Официальная
функция checker, проверки геометрии и T/KPI исполняются из закреплённого исходника.
Полнота, SHA, защищённый C++ регион, формат/таймауты, лимиты и исходная
`aggregate_report` сохранены. Очерёдность суммирования остаётся прежней.
После доказанного отказа новые случаи не запускаются; неполный кандидат
получает отказ и score 0. Валидному кандидату нужны все 128.
